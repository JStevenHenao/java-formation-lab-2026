# Solucion de referencia — decisiones de mapeo

## Decisiones

- `Order.customer` y las referencias desde `OrderItem` usan `LAZY` y no propagan operaciones: el pedido no es propietario del ciclo de vida del cliente ni del producto.
- `Order.items` propaga solo `PERSIST` y `MERGE`, y usa `orphanRemoval`: los ítems son componentes del agregado `Order`. No se propaga `REMOVE` a `Customer` o `Product`.
- El pedido y el producto son obligatorios en `OrderItem`, tanto en la API de dominio como en las llaves foráneas `NOT NULL`. `Order.addItem` es el punto de entrada para crear y asociar ítems; la colección se expone como no modificable.
- `Product.version` evita actualizaciones perdidas mediante optimistic locking. `Address` es un valor opcional embebido en `Customer`, no una entidad con identidad y ciclo de vida propios.
- Los montos usan `DECIMAL(19, 2)`; el estado se almacena como texto estable y las restricciones de cantidad, precio y stock se aplican también en la base de datos.

## DDL propuesto (H2 / PostgreSQL)

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL,
    address_street VARCHAR(160),
    address_city VARCHAR(100),
    address_region VARCHAR(100),
    address_postal_code VARCHAR(20),
    address_country VARCHAR(100)
);

CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    price DECIMAL(19, 2) NOT NULL CHECK (price >= 0),
    stock INTEGER NOT NULL CHECK (stock >= 0),
    version BIGINT NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(20) NOT NULL CHECK (status IN ('PENDING', 'CONFIRMED', 'SHIPPED')),
    created_at TIMESTAMP NOT NULL,
    customer_id BIGINT NOT NULL,
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers(id)
);

CREATE INDEX idx_orders_customer_id ON orders(customer_id);

CREATE TABLE order_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price DECIMAL(19, 2) NOT NULL CHECK (unit_price >= 0),
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders(id),
    CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products(id)
);

CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
```

El DDL no declara `ON DELETE CASCADE`: el ciclo de vida de `OrderItem` se controla en el agregado mediante `orphanRemoval`; borrar un producto referenciado debe rechazarse por la llave foránea, no borrar pedidos.
